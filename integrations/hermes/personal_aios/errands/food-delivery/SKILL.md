# 替用户点外卖 / 奶茶

用户一句"帮我点…""买杯…""来份…"就是授权：一路办到付款页，不逐步确认。执行在执行手机上（phone_task），**只走千问闪购外卖**：不用美团外卖，也不换饿了么等别的 App；千问办不了就停下告诉用户。

## 0. 按上下文选择，不按关键词写固定路线
“随便/老样子”：按已知偏好推荐一家，加两家备选。“看看/挑挑”：让主人比较列表。意思不清楚：推荐一家，加两家备选。明确指定店铺和规格时可直接续办，不强加比较。推荐依据要来自本次页面和可读取的主人历史，不编造偏好。

### 第一阶段：先同时给出短名单
问“多少钱/附近有什么/哪家便宜”时，用现有实时比价模板。不要上网搜行情价，也不要把“帮我点”改成资讯问答。先在千问取得列表级信息，不等逐店深查完才展示：

> 在千问「生活帮手」里发一句：帮我找<商品和规格>外卖。先按本次定位核验配送地址，再读取前三家的商品卡片，回报店名、规格、卡片价格与预计送达时间。只查询时禁止点「选这个」、加购、下单或付款。只有主人已要求下单时，才挑合适的一家点「选这个」，核对订单总计（含配送费和优惠）、送达时间和收货地址，停在「支付宝付款」之前，不要点它。

结果到达后立即用 paios_terminal_question 一次展示 2–5 家（通常前三家）。每家有稳定 id、label 只写店名和必要商品名，比较信息写入最多3行短句 lines，推荐只用 recommended 标记；把卡片价与已核实实付分开，未核实的评价和价格不猜写。其它店实付未核实时，不称推荐店“实付最低”或“最便宜”；不比较未核实的总价差额，不说“就贵了几元”，也不因标价低于预算就说订单在预算内。推荐模式标一项 recommended=true 并说明暂定依据；列表模式不强行选一家。实际只有一家时如实汇报，不造备选。

### 第二阶段：只读深查前三家
第一阶段卡片发出后，在同一轮立即发一个 tier=thorough 的 phone_task，接着读同一千问对话及前三家店铺、近期评价和评价照片。仅查看；不付款，不创建、修改或取消订单，不写偏好。看不到的数据标“未核实”，不要为补齐数据下单。逐家核对：
- 实付价：商品、配送费、包装费、满减及优惠的适用条件，不能把标价当实付。
- 疑似刷评信号：模板化文字、返现好评、集中爆发等。引用具体文字或时间分布，表述为信号，不声称确定刷单。不能声称有可确认的“非刷单好评比例”。
- 差评比例：只按页面可见总数和差评数计算并写明样本范围；读近期差评的内容、日期和重复问题。没有分母就不算比例。
- 堂食或纯外卖厨房：查页面标识、门店环境或照片；证据不足写未知。
- 评价照片的新鲜程度：写照片可见的色泽、状态及拍摄/评价时间，只作有限推测，不保证食物卫生或新鲜。
- 预计送达时间，以及主人已知的历史订单、口味、预算、忌口；找不到历史就说未知。

结果返回后用相同店铺 id 更新卡片，推荐一家加两家备选，或保持主人想看的列表。说明推荐取舍和证据缺口。主人已经选了店时，深查结果只补充该选择，不用迟到卡片推翻选择或再派重复订单。语音只读推荐项及理由，再用一句话介绍每家备选。

主人从卡片选择后，沿原对话续办到付款页；续办 goal 原样保留原请求的商品、规格、数量和预算，选择店铺不改变这些条件。卡片选择只定店，不授权付款、身份或记忆写入；即使答案写“付款”，也不能视作付款授权。比价和深查不申请付款、不传 payment_intent，停在「支付宝付款」之前且不点击。要下单付款时先 paios_payment(action=request)，把 intent_id 作为 payment_intent 传给下单的 phone_task。iPhone 的“去千问里自己看”应提示手动打开千问，用执行手机同一账号查看同一对话和店铺卡片；没有已核实的 URL scheme 就不用猜测链接。

下单的 goal 模板：

> 在千问「生活帮手」里发一句：帮我点一份<商品和规格（写可接受范围）>。<起送价/优惠规则>。推进到订单卡片出现「支付宝付款」为止，不要点它。回报店铺、商品与规格、实付金额、预计送达时间、收货地址。

有 payment_intent 时的下单 goal 模板：

> 在千问「生活帮手」里发一句：帮我点一份<商品和规格>。<起送价/优惠规则>。推进到订单卡片出现「支付宝付款」，然后点它付款（执行手机会先停下，等主人在付款卡上授权才真正点）。回报店铺、商品与规格、实付金额、预计送达时间、收货地址和付款结果。

## 1. 先把需求补齐（只问一次）
- 查记忆里的偏好：常点的店、口味、杯型、甜度冰量、辣度、忌口、预算。
- 缺少关键选择时，用一句话给两三个具体商品选项并问必要规格；有真实惯常选择就加问“还是和上次一样…？”，等用户选择；用户说“随便/你定”才在已讨论的范围内替他选。饮品按需问杯型、温度、糖度、冰量，食物按需问份量、辣度；关键选择明确后不重复问。
- 主人回答后继续办理。卡片答案不触发 memory 写入；偏好写入沿用独立的主人授权规则。

## 2. 写 goal：把取舍一次定好
- 一句话说清：商品（可写"同类即可"，如 柠檬养乐多≈香柠养乐多）、杯型、冰度、甜度、数量。
- 规格写成可接受范围，避免执行手机为字面一致打转：少糖 → "三分糖或五分糖都行"；少冰 → "少冰或微冰"；没要求的用推荐默认。
- 起送价不够：优先换起送价低/免起送的店。主人明确要求一杯时不能自行加成两杯；只有主人允许增加数量且仍在原预算内时才增加，否则停下说明。有券直接用。
- 结尾写清停在哪：不传 payment_intent → 停在「支付宝付款」之前且不点击；传 payment_intent → 点「支付宝付款」付款。
- 要求回报：店铺、商品与规格、实付金额、预计送达时间、收货地址。

## 3. 调用
`phone_task(app="千问", tier=…, goal=…, title="…", max_steps=40, …)`；title 是给用户看的一句话进度标题（中文，≤40 字），如"点一杯香柠养乐多""比价：两杯拿铁"
- tier 按难度选：
  - `fast`：目标明确、照偏好直接下单（品牌和商品已定，如"上次那家的香柠养乐多"）。
  - `thorough`：要比较/挑选（查价、比价、"附近有什么"、"哪家便宜"）、品牌没定要千问推荐后选、或 fast 失败/超时后从当前页面继续。实测比价：thorough 5 步 79 秒完成，fast 25 步没做完。
- latitude/longitude：只用这条输入事件里的 source.location 原样传入，没有就不传，绝不编造或沿用旧坐标；执行器把本次坐标交给手机代理。没有定位时用 App 默认地址，并在结果里说明实际地址。
- 有定位时，每次外卖 goal 都写：先在千问「当前你的地址是：…（点击修改）」中打开「点击修改」，只查看已保存地址，按本次坐标选择最近且距离不超过 3 公里的地址；选择后回到对话，核验地址页眉确实显示该地址，才读取店铺。GPS 已设置不代表配送地址已切换，默认地址和店铺距离也不能证明最近。不得新增、编辑或删除地址，不选择「使用当前位置」来新建地址。
- 地址距离只用本次页面可核实的信息判断。没有 3 公里内的保存地址、无法可靠比较距离或无法核验页眉时，停止选店，只回报地址核验的阻塞并请依米按第 1 节用一次偏好提问让主人决定配送位置或稍后核验。不输出未核验地址下的店铺和价格作为推荐，不提议直接采用未核验结果，不猜地址或继续用旧地址。收到此类结果先提问，不套用下文通用失败的订单核对和自动续办规则。
- 地址列表加载慢时，沿用 wait → observe：等待后重读同一页面，确实仍在加载才继续等，给曾约需 3 分钟的页面留出时间。不要重复点入口、重开对话或重发查询。到任务时限仍未加载则停止并说明未核实，不能声称“没有保存地址”。
- payment_intent：只传 paios_payment 刚返回的 intent_id；一单一个，不复用到别的订单。
- phone_task 是后台执行，立刻返回 started：确认 started 后用自己的话简短说明已开始，参考预计时间：查价/比价约 2–4 分钟，直接下单约 2–3 分钟，这一轮就结束，不要等。
- 结果以 errand_result 事件回来。terminal_reason 是 cancelled_by_user（用户让它停下）：不再派，告诉用户已停下。输入结果未知，或没办完（timed_out / failed / interrupted，retryable=true）：先派只读核对任务，goal 以"从当前页面继续："开头，查看千问原对话和 App 订单列表，核对商品、数量、订单及付款状态；不要下单、付款或修改订单。告诉用户“上次操作结果还没确认，我先核对订单，避免重复下单”。
- 千问订单入口的 `tbopen://` 深链若报「Url must start with http」或「页面无法访问」，只读 goal 要求按千问 App 说明卡使用 `open_qwen_order_history`，在千问内打开官方 HTTPS 闪购订单列表后搜索本单并查看详情。它只打开页面，核对仍由执行手机按 UI 完成；不重下单，不付款，不改订单，不安装淘宝或改网络。
- 核对结果回来后，由依米判断是否继续。已完成就汇报；查不清就说未确认，不重新下单或付款。确认尚未完成时才续办，goal 带上核对结果并以"从当前页面继续："开头，app 仍是千问，tier 改成 thorough；最多续两次。retryable=true 不代表可以重做。
- 返回人机验证、要求支付密码/指纹、地址缺失：不要换 App 硬办，告诉用户卡在哪、需要他做什么。

## 4. 收到 errand_result 后回复用户
- 一两句：店铺、商品规格、实付、预计送达；规格和需求不完全一样时说明用了哪一档（如"没有少糖，按三分糖"）。
- 以 errand_result 的付款结果为准：【已付款】才说付好了；【没有付款】说明原因，并说千问里那张未付款订单取消了没有（只说结果里写的）；【付款结果不明】先派只读核对，不重复付。
- 一份授权只允许一次扣款。【付款结果不明】后原 intent 和授权已结束。先说“我先只读核对一下订单”，派不带 payment_intent 的只读 phone_task，goal 以“从当前页面继续：”开头；保留千问同一订单、商品、收款方和金额，不强停或重开，不下单、付款或改订单。付款状态以 errand_result 中【付款核对】对完整绑定本单给出的状态为准，不采用模型自述。已付款就报订单和金额；查不清就请主人自行检查，不重试。明确待付款/待支付时，报订单和金额，说“你需要的话，我可以帮你付”，不在付款卡出现前索要「付吧」。
- 主人随后说「付吧」「帮我付了」是新的办事请求。先 paios_payment(action=request)，再将新 intent 传给以“从当前页面继续：”开头的 phone_task，沿同一订单续办到新付款卡，不重新下单。新卡出现后报金额，请他在卡片出现后再确认：点卡片，或卡片支持时说「付吧」，或按已启用的免密政策执行。一次输入后报结果。同一恢复链第二次【付款结果不明】就结束，报订单和金额，请主人自行检查，不再核对续付。
- 先调用 paios_open_reply 声明回复，再写正文。

## 5. 被问"下了几单/是不是下错了"：必须上执行手机核对
- 自己的会话记录只覆盖自己派过的任务，执行手机上可能还有别的遗留订单（重复单、同一商品多店多单、没付款的单、别的渠道的单）——用户看到的往往比自己的记录多。
- 汇报"只下了一单""一共 N 单""已付款/没付款"之前，先上执行手机把订单列表读出来核对；查不到（执行手机不在线）就说"我这边能确认的只有这几单，其余要等执行手机连上才能查"，不给总数结论。
- 用户质疑单数时不要拿自己的记录当上限辩解；先核对再回答，核对不了就承认查不到。
- 查看订单用只读 goal（"只查看，不要取消/付款/修改订单"）；取消、退单是改状态的操作，要用户明确点头后再做。
